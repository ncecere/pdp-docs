An agent in Pi Durable Platform is one deployed instance of a template, in one team. Editors, admins and owners deploy and change agents; admins and owners delete them.

## Deploy one

Choose **Deploy agent** on the team's **Agents** page, on **All agents**, or on a template's page in the **Catalog**.

<Steps>
<Step>

Pick the **template**: one from the catalog, or one of the team's own. On a template's page it is already chosen.

</Step>
<Step>

Pick the **team**, if you're an editor on more than one.

</Step>
<Step>

Give it a **name**, unique in the team (1 to 100 characters on one line), and optionally a description.

</Step>
<Step>

Leave **Model** on **Template's model**, or choose another model the team may use: the platform's models published to the team, and the team's own. You can change it later.

</Step>
</Steps>

The agent opens on its **Test** tab. Deploying doesn't start it: its first message does.

## Its pages

An agent has these tabs:

- **Overview**: its status (running now or hibernated, turned off), template and version, model, tools (the MCP servers it can call), storage, its usage over the last 30 days, and **Use it from your app** with example requests. While it runs, the status says what keeps it awake (a reply, an open stream, background work, recent use) or that nothing does and it hibernates shortly.
- **Test**: a chat with it ([Testing an agent](/docs/use/test-chat)).
- **Approvals** (since v0.4): its tool calls waiting for a person, and recent decisions ([Tool approvals](/docs/teams/tool-approvals)).
- **Triggers** and **Runs** (since v0.4): the schedules and webhooks that start it without a person, and each run they started ([Triggers and runs](/docs/teams/triggers)). Service-managed agents have neither.
- **Conversations**: only for platform admins ([Reading conversations](/docs/administer/reading-conversations)).
- **Settings**: name, description and model; turning it off; moving it to another team; deleting it.

While the agent is running, its page header has **Hibernate**, which stops its runtime now; the next request wakes it. Any member can use it; platform staff who aren't on the team can't (since v0.1.1).

### When it can't start on its runtime

If the Overview says **The agent can't start on its runtime**, the platform refused to start it on a runtime older than the one that last wrote its conversations. Requests that would wake it answer `409 runtime_too_old`. It happens after the operator rolls the runtime image back; the fix is to deploy the current runtime again. See [Doctor and health](/docs/operate/doctor-and-health#common-problems).

## Upgrade to a new version

An agent stays on the template version it was deployed with. When the template has a newer version, the Overview offers **Upgrade to v…**. You can also move it to any version, newer or older, with the API (`templateVersion`).

A running agent hibernates at once and starts on the new version with its next message. Its conversations are kept.

## Change its model

In **Settings**, choose another model the team may use, or go back to **Template's model**. As with an upgrade, a running agent hibernates and starts on the new model with its next request. Each thread moves to the agent's current model with its next message, so older threads answer on the new model too.

If a platform admin turns off or unpublishes the model an agent runs on, its Overview says **Its model isn't available** and the agent doesn't start until someone chooses another model.

## Turn it off

**Turn off agent** in **Settings** hibernates it and refuses new messages, from the console and from apps; its conversations are kept but can't be read until it's turned on again. Apps get an error on their next message. A request that was already under way when you turned it off doesn't start it again.

## Move it

**Move agent…** in **Settings** (owners and admins of both teams) moves the agent, with its conversations, to another team or to your personal workspace. The dialog shows what changes before you confirm. Its triggers are deleted. See [Moving an agent](/docs/use/moving-an-agent).

## Delete it

**Delete agent** in **Settings** (owners and admins) deletes the agent, its database schema and role, and every conversation. Apps using it get errors. This can't be undone.

## Service-managed agents

An app with an editor [service account](/docs/teams/service-accounts) can create agents in your team with its own **external key**, typically one per user of the app (see [Agents for your app's users](/docs/build/agents-by-key)). These agents are **service-managed**:

- Only the team's service accounts use them. Members don't see them at all.
- The team's owners and admins see them in **Agents**, marked **Service-managed**, with their external key, status and last use, but never their conversations, and can delete them.
- Editor service accounts can change and delete them.
- They can't be moved to another team.
- They don't count towards the team's limit of 50 agents.

In a shared team, an agent with an external key is always service-managed: the database enforces it. An agent a person gets by key in their own personal workspace isn't service-managed: it's theirs like any other.

## Names and limits

Names are unique in the team, ignoring case, among agents made by hand. A team may have up to 50 agents made by hand. A personal workspace has its own limits: see [Your personal workspace](/docs/use/personal-workspace).
