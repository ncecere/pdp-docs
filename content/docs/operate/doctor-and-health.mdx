## doctor

`pi-durable-platform doctor` checks an install without changing anything, using the same configuration as `serve`:

1. **Configuration**: loads it and validates it for `serve` (or `--mode migrate`).
2. **Safety**: the [production safety checks](/docs/operate/configuration#production-safety-checks).
3. **PostgreSQL**: connects to the platform database and reports its version and the time it took.
4. **Migrations**: whether the database is at the binary's migration.
5. **Keys**: which pepper the usable API keys are on, which `ENCRYPTION_KEY` every stored secret is sealed with, and (since v0.4) which key signs MCP identity tokens.
6. **Group re-check** (with `OIDC_ALLOWED_GROUPS`): how many recently active people the platform can't re-check, because it has no refresh token for them.
7. **Agents database** (since v0.1.1): connects to `AGENTS_DATABASE_URL` and checks that its role can provision agents. It reads the role's attributes and privileges and creates nothing.
8. **Agent roles**: whether the agents database has roles left behind by agents that no longer exist.
9. **Database access**: whether `PUBLIC`, and so an agent's role, may connect to the platform database or to other databases on the agents database's server.

Each check ends as **ok**, **info** (worth knowing), **warn** (something to do, but the platform works) or **fail**. `doctor` exits 1 only when a check fails: a warning exits 0.

## The keys checks

| Check | OK when | Otherwise |
|---|---|---|
| `keys pepper` | Every usable key, service account key and app token is under `API_KEY_PEPPER` | **Info** while some are on `API_KEY_PEPPER_PREVIOUS` (they move when used), or on a pepper no longer configured (those no longer work: revoke them). **Info** too when none is left on the previous pepper: you can remove it |
| `keys encryption` | Every stored secret is sealed with `ENCRYPTION_KEY` | **Warn** while any value is still sealed with `ENCRYPTION_KEY_PREVIOUS`, naming the columns and counts: run `rekey`, then remove the previous key. **Fail** when a value is sealed with neither key, since the platform can't read it. **Info** when none is under the previous key and `ENCRYPTION_KEY_PREVIOUS` can go |
| `keys mcp-identity` (since v0.4) | A key signs [MCP identity tokens](/docs/build/mcp-identity) now; says which and since when, and counts keys waiting to sign | **Warn** when there is no key yet (`serve` creates it at start) or the signing key is older than 90 days: [rotate it](/docs/operate/key-rotation#the-mcp-identity-signing-key) (only **info** once its successor is published). **Fail** when keys exist but none signs now |

The `keys encryption` check covers every sealed column that [`rekey`](/docs/operate/key-rotation) knows, including the identity provider refresh tokens that [group re-checks](/docs/operate/oidc#re-checking-groups) keep (`user_idp_tokens`). It reads only the key IDs stored with the values, and opens nothing. See [Rotating keys](/docs/operate/key-rotation).

## The group re-check check

With `OIDC_ALLOWED_GROUPS` set, `auth group re-check` counts the recently active people (a sign-in, a session, or an API key or connected app used in the last 30 days) by whether a refresh token is stored for them.

| Result | Meaning |
|---|---|
| **info** | Everyone recently active has a token and is re-checked every interval; or nobody is recently active yet; or the re-check is off (`OIDC_GROUP_RECHECK_INTERVAL=0`) |
| **warn** | Some recently active people have no stored token. They are never re-checked, and keep access after leaving the allowed group until they sign in again. The fix: add `offline_access` to `OIDC_SCOPES`, allow refresh tokens for this client in your identity provider, and have people sign in again |

Without `OIDC_ALLOWED_GROUPS` there is no such line. See [Re-checking groups](/docs/operate/oidc#re-checking-groups).

## The agents database checks

| Check | OK when | Otherwise |
|---|---|---|
| `agents database` | The database answers; reports its PostgreSQL version, the database and the role | **Fail**, with the connection error (never the URL or its password). If the database doesn't exist yet and `AGENTS_CREATE_DATABASE=true`, it's **info**: `serve` creates it. |
| `agents provisioning` | PostgreSQL **16 or later**, and the role has **`CREATEROLE`** and **`CREATE`** on the database (or is a superuser) | **Fail**, naming what's missing, with the fix: `ALTER ROLE <role> CREATEROLE; GRANT CREATE ON DATABASE <db> TO <role>` (or make the role the database's owner), or move to PostgreSQL 16 or later |

Each agent gets its own role and schema in the agents database, which is why the platform's role needs `CREATEROLE` and `CREATE`; PostgreSQL 16 is the first version that lets it grant itself membership of each agent role the way provisioning does. See [Databases](/docs/operate/databases).

Without `AGENTS_DATABASE_URL` the checks are skipped, reported as info ("agents can't be deployed"): the configuration checks already say whether your launcher needs it.

### The agent roles check

Roles are server-wide in PostgreSQL, so dropping or recreating the agents database leaves its agents' roles behind. When the provisioning check passes, `agents roles` lists the roles named like agents' (`agent_…`) that belong to no agent in the platform database and have no schema in the agents database.

| Result | Meaning |
|---|---|
| **ok** | Every agent role belongs to an agent, or to a schema in the agents database |
| **info**, with names | These roles belong to no agent. Run `pi-durable-platform prune-roles --dry-run`, then `prune-roles`. It also counts roles that look like agents' but that `prune-roles` would leave alone |
| **info**, skipped | The platform database is unavailable or its migrations are pending, so the agents' roles are unknown |

See [Databases and roles](/docs/operate/databases#clean-up).

### The database access checks

An agent's role is a login role of the database server. PostgreSQL lets `PUBLIC` connect to every database it creates, so unless you revoke that, an agent's role can open the platform database and take its advisory locks. These checks **warn**, never fail:

| Check | OK when | Otherwise |
|---|---|---|
| `postgres public-connect` | `PUBLIC` may not connect to the platform database, or the agents database is on another server | **Warn**, with the fix: `REVOKE CONNECT ON DATABASE <platform database> FROM PUBLIC; GRANT CONNECT ON DATABASE <platform database> TO <the platform's role>;`, and the same grant for any other role that uses it |
| `agents public-connect` | `PUBLIC` may connect to no other database on the agents database's server | **Warn**, naming those databases: revoke `CONNECT` on them too (and grant it back to the roles that use them), or limit agent roles to the agents database in `pg_hba.conf` |

`doctor` decides whether the two databases share a server by comparing the servers' start times. The second check runs only when they do. See [Where agent roles can connect](/docs/operate/databases#where-agent-roles-can-connect).

```sh
pi-durable-platform doctor            # text report
pi-durable-platform doctor --json     # for scripts
pi-durable-platform doctor --timeout 20s
pi-durable-platform doctor --mode migrate   # validate the configuration for `migrate` only
```

It exits 1 if any check fails, with a fix for each failure or warning. The image has no shell; on Kubernetes run:

```sh
kubectl -n pi-durable-platform exec deploy/pi-durable-platform -- /pi-durable-platform doctor
```

`doctor` doesn't check the Kubernetes API or the identity provider: deploying and testing an agent covers them. The readiness probe also checks that the agents database answers.

## Probes

| Path | Answers |
|---|---|
| `GET /healthz` | Liveness: the process is up |
| `GET /readyz` | Readiness: both databases answer and the platform isn't shutting down |

On SIGTERM `/readyz` fails first, for `SHUTDOWN_DELAY`, so load balancers stop sending traffic before the server stops. With several replicas, each one does this in turn during a rollout: see [Running several replicas](/docs/operate/replicas).

## Logs

The platform logs to standard output, as JSON by default (`LOG_FORMAT`, `LOG_LEVEL`). Every response carries an `X-Request-ID` header; the same ID is in the logs and in audit entries, so you can follow one request. Secrets, keys and tokens are never logged.

The platform also exports Prometheus metrics, on a port of its own, and OpenTelemetry traces if you set a collector. When there is a trace, the access log carries its `trace_id`. See [Metrics and tracing](/docs/operate/metrics-and-tracing).

## Common problems

| Symptom | Cause |
|---|---|
| Refuses to start: "the database is at migration N but this binary needs M" | Run `migrate`, or set `MIGRATE_ON_START=true` |
| Refuses to start naming `DEV_AUTH`, `AGENTS_LAUNCHER=local`, an example key or an `http` `APP_URL` | A production safety check: see [Configuration](/docs/operate/configuration#production-safety-checks) |
| "agents database not ready; retrying" in the logs | The platform waits for the agents database at start-up; check `AGENTS_DATABASE_URL` and the network, and run `doctor` |
| Deploying an agent fails with a permission error on the agents database | The platform's role lacks `CREATEROLE` or `CREATE` on the database, or the server is older than PostgreSQL 16: `doctor`'s `agents provisioning` check says which |
| Agents answer `503 agent_unavailable` | The runtime didn't start in time: check the agent pod's events and logs, the image, `AGENTS_IMAGE_PULL_SECRET`, quotas |
| Agents start but every reply fails | Agents can't reach `AGENTS_GATEWAY_URL` (the gateway listens on `127.0.0.1` by default), or the model's provider refuses: see the thread's last error |
| Everyone is refused at sign-in with "A verified email address is required" | Your provider doesn't send `email_verified`: see [OIDC sign-in](/docs/operate/oidc) |
| An agent answers `409 runtime_too_old`, and its Overview says **The agent can't start on its runtime** | A runtime with a newer Pi durable package wrote the agent's data, and the runtime image now deployed is older: deploy the current runtime again (rolling a runtime back is not supported). If the runtime is current and the agent is still refused, the recorded version is wrong: `pi-durable-platform reset-storage-version --agent <id>` removes it (the next start records its own), or `--to <version>` sets it. It's audited. Never reset below a version that really wrote the agent's data |
| MCP requests fail with `503 identity_unavailable` | The platform can't sign identity tokens, for example after `ENCRYPTION_KEY` changed without `ENCRYPTION_KEY_PREVIOUS`: see `keys mcp-identity` above |
| An agent never hibernates | Its Overview says what keeps it awake: a reply, an open event stream, background work (up to `AGENTS_BACKGROUND_MAX`) or recent use |
