## One enforcement point

Apps and browsers reach agents **only through the platform**. It authenticates every request, checks the caller's role in the agent's team and the thread's visibility, then relays the conversation. Runtimes are never exposed: each accepts only its own per-agent bearer token, which only the platform holds. Not allowed reads as not found, so the API doesn't reveal that another team's agent, or another person's private thread, exists.

## Isolation between agents

- **Storage**: one schema and one database role per agent, in a database apart from the platform's. A role owns only its schema and has no rights elsewhere. See [Databases](/docs/operate/databases).
- **Runtime**: one process (one pod) per running agent, non-root, read-only root filesystem, no capabilities, no Kubernetes service account token. `AGENTS_RUNTIME_CLASS` can add a sandboxing runtime such as gVisor.
- **Single owner**: an agent's owner is recorded in a table in the agent's **own schema**, tied to the database session of its runtime's only connection. A stale runtime that loses its connection loses its ability to write at the same moment its session ends, and a replacement takes over as soon as it does, so two runtimes never write one agent.

  Because the record is in the agent's own schema, no other agent's role can write it, lock it, drop it, or read it: each gets "permission denied". That is why another agent's role can't block an agent from starting or take over its storage, which a database-wide advisory lock couldn't prevent: any role in the agents database could take another agent's lock key. A role can still see that other roles' sessions exist, and agents share the server's capacity, so a hostile agent could remain a noisy neighbour. See [Databases and roles](/docs/operate/databases#who-owns-an-agent).
- **Network**: in proxy mode agents need no path but the platform's gateway and their database. See [Network isolation](/docs/operate/network-isolation).

## What it trusts

Agents run **templates**, not uploaded code: instructions, a model and MCP servers, on the platform's own runtime image. Team templates reach other teams only after a platform admin's review. Teams can't run code of their own; that needs stronger isolation first (see Known limits).

## Teams and people

- Team and platform roles are checked in the same database transaction as each change, and each change is audited in that transaction.
- Platform roles never reach conversations. Platform admins and auditors see every team's agents (settings, status, usage) read-only: they can't use, change or hibernate them (since v0.1.1 hibernating another team's agent answers 403). A platform admin's read of a conversation needs a reason and is recorded in the team's log.
- Personal API keys act as their person. Apps connected with OAuth Connect act as their person **without** the platform role. Service accounts act in their own team only.
- Administration, members, keys and service accounts need a browser session: a stolen key can't create more keys or change roles.

## Browser sessions

Sessions are cookies (`Secure` on https), lasting `SESSION_TTL`. Writes from the browser need the session's CSRF token and a same-origin `Origin`. Suspending a person ends their sessions.

## Who may sign in, and for how long

If `OIDC_ALLOWED_GROUPS` is set, the platform keeps asking the identity provider whether people are still in an allowed group, so removing someone from the group ends their access within a check interval instead of at some later sign-in. For a person it finds outside the group, or whom the provider no longer vouches for, the platform:

- **ends their browser sessions** and **disconnects their connected apps**;
- **ends their open event streams** within 30 seconds, as for a suspended person;
- **stops their personal API keys from working**, without revoking them;
- keeps their data, team memberships and agents.

This is separate from **Suspend…**, which only an admin does: neither undoes the other. The person comes back by signing in again once the provider lists them in an allowed group. Each denial and each restoration is in the audit log. It needs the provider to issue refresh tokens: see [Re-checking groups](/docs/operate/oidc#re-checking-groups) for what to set, what the grace period is, and what isn't covered.

## Thread MCP servers have a known creator

An app can give a thread its own MCP servers. They belong to a thread whose creator the platform knows. Setting servers on a thread ID that has no record **starts the thread**, the caller being its creator, as its first message would. A thread's servers are never kept without a thread. So nobody can leave servers on an ID for someone else's later private thread to inherit, which a client-chosen thread ID allowed before. Whoever uses an ID later gets the normal rules of the thread they find: a shared thread they may join, or a private thread that answers `404 thread_not_found`. While a thread has no message yet, only its creator may change its servers, and someone else's first message drops them. See [Thread MCP servers](/docs/build/thread-mcp-servers#whose-thread-it-is).

Threads that the platform names itself, with an unguessable ID (`POST /v1/agents/{id}/threads`), can't be guessed or pre-empted at all. See [Threads, messages and events](/docs/build/threads-and-messages#start-a-thread).

## Secrets and keys

- **Provider keys, MCP headers, apps' thread MCP headers, each agent's database password and runtime token, and the identity provider refresh tokens kept for group re-checks** are encrypted with `ENCRYPTION_KEY` and never returned by the API. Agents get provider keys only for direct-mode providers and the platform's default model; in proxy mode the gateway adds them.
- **API keys, service account keys and OAuth tokens** are stored only as HMAC-SHA256 digests under `API_KEY_PEPPER`. They are shown once, never logged.
- **Runtime tokens and database passwords** reach Kubernetes runtimes through a per-agent Secret, never the pod spec; with a warm pool, through the activation request, stored nowhere in Kubernetes.

### Rotating keys

- **`API_KEY_PEPPER`**: set the new value, and the old one as `API_KEY_PEPPER_PREVIOUS`. Keys made with the old pepper keep working and are re-digested on their next use (`*.pepper_rehash` in the audit log). `doctor` counts keys still on the old pepper. After 2 to 4 weeks, remove `API_KEY_PEPPER_PREVIOUS`; keys not used by then stop working.
- **`ENCRYPTION_KEY`**: set the new value, and the old one as `ENCRYPTION_KEY_PREVIOUS`; restart; run `pi-durable-platform rekey` to re-seal every stored secret under the new key; check `doctor`; then remove the old key. See [Rotating keys](/docs/operate/key-rotation) for the steps and for what `rekey` does and doesn't do.
- **The warm pool's activation token**: see [Agent Sandbox](/docs/operate/agent-sandbox#rotating-the-activation-token).

## What metrics and traces reveal

The metrics port has **no authentication**: keep it on a private network, never behind the Ingress, and let only your scraper reach it. What it serves is aggregate. A metric label never holds a person, a team, an agent, a thread or a URL, and a trace span never holds message content, headers, URLs, keys, tokens or a person's identity. The product's tests check both. See [Metrics and tracing](/docs/operate/metrics-and-tracing#what-the-labels-never-contain).

## Addresses others choose

Teams' own providers and MCP servers, apps' metadata documents and apps' MCP servers are addresses chosen by teams or apps. The platform guards them (public addresses, admin-listed private networks, allowed hosts, no redirects, DNS pinned per connection). See [Network isolation](/docs/operate/network-isolation#what-the-platform-guards-itself).

## Known limits

- **Agents share the database server**: every agent role can see that other roles' sessions exist, and there are no per-role quotas beyond a connection limit. Cross-agent interference with ownership is closed, but uploaded agents would still need a storage proxy instead of database credentials, or hostile-code isolation.
- **A compatibility lock stays for now**: runtimes also take the older release's advisory lock while any older runtime may still run. It is for rolling upgrades and is to be removed later.
- **No hostile-code isolation yet**: running teams' own code needs sandboxed runtimes (gVisor or Kata) first.
- **Shared agent tools**: every thread of an agent uses the same MCP credentials. Private threads hide conversations, not what an MCP server stores.
- **Client-chosen thread IDs can be guessed if the client picks guessable ones**: whoever uses an ID first starts that thread. A shared thread can then be joined by anyone who may use the agent, and a private one is `404` for everyone else. Use `POST /v1/agents/{id}/threads`, or random IDs.
- **Group re-checks have gaps**: the bootstrap admin and development personas are never re-checked, and people whose provider issued no refresh token are checked only when they sign in. See [Re-checking groups](/docs/operate/oidc#what-isnt-covered).
- **Database roles are server-wide**: agent roles outlive a dropped agents database. `doctor` lists them and `prune-roles` drops them.
- **The database server is a trust boundary you configure**: unless you revoke it, an agent's role may connect to the platform database and other databases on its server. See [Where agent roles can connect](/docs/operate/databases#where-agent-roles-can-connect); `doctor` warns until it's closed.
- **Open streams and keys**: an event stream closes within 30 seconds when a person loses access, but a revoked API key, app grant or service account key doesn't close a stream that is already open.
- **A `404` reveals a private thread's ID**: on a client-chosen ID, `404 thread_not_found` tells the caller that the ID is someone's private thread. Platform-chosen IDs can't be probed this way.

Stronger sandboxing, to run teams' own code, is planned on the project's [roadmap](https://github.com/ncecere/pi-durable-platform/blob/main/docs/roadmap.md).
