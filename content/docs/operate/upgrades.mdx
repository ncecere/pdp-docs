## Migrations

The platform database's schema is managed by migrations built into the binary. They are forward-only: a release never edits a migration an earlier release applied, it adds the next one. v0.1.0, v0.1.1 and v0.1.2 have 16 (v0.1.1 and v0.1.2 added none). v0.2 adds migration 17.

Apply them either way:

- **At start-up**, with `MIGRATE_ON_START=true`.
- **As a step of your rollout**, with `pi-durable-platform migrate`, which applies them and exits. It needs only `DATABASE_URL`.

A platform whose database is behind the binary refuses to start, naming both migration numbers. `pi-durable-platform doctor` reports the migration state.

The **agents database** has no migrations of its own: agent schemas are created by the platform, and their tables by Pi's durable package in each runtime.

## Upgrading

<Steps>
<Step>

Read the release notes for the version you're moving to, and back up both databases (see [Backups](/docs/operate/backups)).

</Step>
<Step>

Verify the new images' signatures and note their digests.

</Step>
<Step>

Run the new version's `migrate`, or let `MIGRATE_ON_START` do it.

</Step>
<Step>

Roll out the platform with the new image, and set `AGENTS_IMAGE` (and your warm pool's image, if you use one) to the **same release** of the runtime image.

</Step>
<Step>

Run `doctor`, then deploy and test an agent.

</Step>
</Steps>

## Upgrading to v0.2

v0.2 changes a few things you should know before you upgrade from v0.1.x:

- **Migration 17** drops the MCP servers that apps had set on thread IDs with no thread, and from then on a thread's servers belong to a thread record (deleting a thread deletes its servers). It adds the state for [group re-checks](/docs/operate/oidc#re-checking-groups) and for threads reserved by `POST /v1/agents/{id}/threads`. With one replica replaced at a time, a request from the old release that sets servers on an unstarted thread fails against the new schema while the rollout runs.
- **Group re-checks** are on by default (`OIDC_GROUP_RECHECK_INTERVAL=15m`) when `OIDC_ALLOWED_GROUPS` is set. They need `offline_access` in `OIDC_SCOPES`. People who signed in before the upgrade have no refresh token stored, so their groups apply when they next sign in.
- **Agent ownership** moves to a table in each agent's own schema. The runtime creates it when it next starts an agent, so agents upgrade as they next wake. During a rollout, runtimes of both releases can run side by side: the new one also takes the old advisory lock. Rolling back to a v0.1.x runtime works; it ignores the table.
- **`rekey`, `prune-roles`** and the new `doctor` checks are available. If you rotated `ENCRYPTION_KEY` before and kept `ENCRYPTION_KEY_PREVIOUS` for that, you can now [finish the rotation](/docs/operate/key-rotation).
- **Deploying** has a [Helm chart](/docs/operate/kubernetes) and [Kustomize](/docs/operate/kustomize) resources. If you installed from hand-written manifests, you needn't move to them, but compare your platform Role with the chart's: the launcher needs `watch` on pods (and on sandboxes and sandbox claims for Agent Sandbox).

## Running agents during an upgrade

Runtimes that are running keep their image until they hibernate. Their next wake starts the new runtime image. To move every agent at once, hibernate them: delete their `agent-…` pods (or Sandbox claims), and the next request starts each one fresh. Their conversations are in PostgreSQL and carry over.

Open event streams end when a platform pod stops; clients reconnect to the new one.

## Rolling back

Migrations don't go backwards. To return to an older version after a migration ran, restore the databases from the backup you took before the upgrade.

## Pi's durable package

The runtime pins Pi's durable package (1.3.0 in v0.1.2) and stores its state in PostgreSQL through a small SQL layer. Upgrading that package comes with a platform release, after Pi's own storage conformance suite passes on PostgreSQL.
