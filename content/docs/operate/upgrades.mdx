## Migrations

The platform database's schema is managed by migrations built into the binary. They are forward-only: a release never edits a migration an earlier release applied, it adds the next one. v0.1.0, v0.1.1 and v0.1.2 have 16 (v0.1.1 and v0.1.2 added none). v0.2.0 adds migration 17.

Apply them either way:

- **At start-up**, with `MIGRATE_ON_START=true`.
- **As a step of your rollout**, with `pi-durable-platform migrate`, which applies them and exits. It needs only `DATABASE_URL`.

A platform whose database is behind the binary refuses to start, naming both migration numbers. `pi-durable-platform doctor` reports the migration state.

The **agents database** has no migrations of its own: agent schemas are created by the platform, and their tables by Pi's durable package in each runtime.

## Upgrading

<Steps>
<Step>

Read the release notes for the version you're moving to, and back up both databases (see [Backups](/docs/operate/backups)).

</Step>
<Step>

Verify the new images' signatures and note their digests.

</Step>
<Step>

Run the new version's `migrate`, or let `MIGRATE_ON_START` do it.

</Step>
<Step>

Roll out the platform with the new image, and set `AGENTS_IMAGE` (and your warm pool's image, if you use one) to the **same release** of the runtime image.

</Step>
<Step>

Run `doctor`, then deploy and test an agent.

</Step>
</Steps>

## Upgrading to v0.2

v0.2.0 changes a few things you should know before you upgrade from v0.1.x. The [release notes](/docs/releases/v0-2-0#upgrading-from-v012) have the steps in order.

- **Migration 17** does four things. It **drops the MCP servers** that apps had set on threads that were never started (no one has used the thread ID yet). It makes a thread's servers belong to a thread record, so deleting a thread deletes its servers. It adds **reserved threads**, those created by `POST /v1/agents/{id}/threads` that have no message yet. And it adds the state for [group re-checks](/docs/operate/oidc#re-checking-groups): the columns that record why a person's access ended, and the table `user_idp_tokens` for the refresh tokens.
- **Group re-checks** are on by default (`OIDC_GROUP_RECHECK_INTERVAL=15m`) when `OIDC_ALLOWED_GROUPS` is set. They need `offline_access` in `OIDC_SCOPES` (the Helm chart adds it; with environment variables or Kustomize you set it), and your identity provider must issue refresh tokens for it. **People who signed in before the upgrade are not re-checked until they sign in again**: no refresh token is stored for them yet, so their groups apply at their next sign-in. Nobody is locked out by the upgrade.
- **A rolling upgrade has both versions running** when you run several replicas. After migration 17, requests handled by a replica of the old version that set MCP servers on a thread with no record fail against the new reference, until every replica runs the new version. The rollout is short: an app can retry once it has finished. See [Running several replicas](/docs/operate/replicas).
- **Several replicas** are supported. Agents that were running before the upgrade have an older runtime, which doesn't report `openStreams`; until each restarts, the reaper judges it by the streams its own replica has seen. They restart when they next wake.
- **Agent ownership** moves to a table in each agent's own schema. The runtime creates it when it next starts an agent, so agents upgrade as they next wake. During a rollout, runtimes of both releases can run side by side: the new one also takes the old advisory lock. Rolling back to a v0.1.x runtime works; it ignores the table.
- **`rekey`, `prune-roles`** and the new `doctor` checks are available. If you rotated `ENCRYPTION_KEY` before and kept `ENCRYPTION_KEY_PREVIOUS` for that, you can now [finish the rotation](/docs/operate/key-rotation). `rekey` re-seals the stored identity provider refresh tokens too.
- **Deploying** has a [Helm chart](/docs/operate/kubernetes) and [Kustomize](/docs/operate/kustomize) resources. If you installed from hand-written manifests, you needn't move to them, but compare your platform Role with the chart's: the launcher needs `watch` on pods (and on sandboxes and sandbox claims for Agent Sandbox). Give the pod a `terminationGracePeriodSeconds` of at least `SHUTDOWN_DELAY` plus `SHUTDOWN_TIMEOUT` (65 s by default; the chart uses 75).
- **Metrics and tracing** are new, and off unless you set `METRICS_ADDR` or `OTEL_EXPORTER_OTLP_ENDPOINT`. See [Metrics and tracing](/docs/operate/metrics-and-tracing).
- **Keep agents' roles out of the platform database.** Run `doctor` after the upgrade. If it warns that PUBLIC may connect to the platform database, revoke that on the database server, as the database's owner, and grant it to the platform's role (and any other role that uses the database):

  ```sql
  REVOKE CONNECT ON DATABASE <platform database> FROM PUBLIC;
  GRANT CONNECT ON DATABASE <platform database> TO <the platform's role>;
  ```

  Do the same for the other databases on that server that agents must not reach, or limit agent roles to the agents database in `pg_hba.conf`. The platform doesn't do this itself, because other roles may use those databases. See [Where agent roles can connect](/docs/operate/databases#where-agent-roles-can-connect).

## Running agents during an upgrade

Runtimes that are running keep their image until they hibernate. Their next wake starts the new runtime image. To move every agent at once, hibernate them: delete their `agent-…` pods (or Sandbox claims), and the next request starts each one fresh. Their conversations are in PostgreSQL and carry over.

Open event streams end when a platform pod stops; clients reconnect to the new one.

## Rolling back

Migrations don't go backwards. To return to an older version after a migration ran, restore the databases from the backup you took before the upgrade.

From v0.2.0 to v0.1.2, the old images also run on the new schema, which stays at migration 17, with two effects. v0.1.2 ignores group denials, so people who lost access get their API keys back until you upgrade again. And a request that sets MCP servers on a thread with no record fails. See [Rolling back](/docs/releases/v0-2-0#rolling-back) in the release notes.

## Pi's durable package

The runtime pins Pi's durable package (1.3.0 in v0.2.0) and stores its state in PostgreSQL through a small SQL layer. Upgrading that package comes with a platform release, after Pi's own storage conformance suite passes on PostgreSQL.
