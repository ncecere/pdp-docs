Pi Durable Platform ships a **Helm chart**. It deploys the platform, the namespace agents run in, the permissions the platform needs there, and the NetworkPolicies that keep agents apart from each other and from the cluster. The same objects are also available as [Kustomize](/docs/operate/kustomize) resources, and [the objects by hand](/docs/operate/manual-manifests) are described as a reference.

Names such as `pi-durable-platform` and `agents.example.com` are placeholders.

## What the chart deploys

- **The platform**: one Deployment (one replica by default; [two are supported](/docs/operate/replicas)), with a Service for the web app and API (port 80, to 8098) and a separate Service for the gateway agents call for models (8099). It runs as a non-root user, with a read-only root filesystem, no capabilities and the default seccomp profile.
- **Metrics**: a port named `metrics` (9090) and a Service `<release>-metrics` for it, which no NetworkPolicy lets anyone reach until you name your scraper. See [Metrics and tracing](/docs/operate/metrics-and-tracing).
- **The agents namespace** (`pi-durable-agents` by default), with the `restricted` Pod Security level. Agent pods, or Agent Sandbox runtimes, run here and nothing else does.
- **Permissions**: a ServiceAccount for the platform, and a Role and RoleBinding **in the agents namespace only**, with exactly the verbs the launcher uses. Nothing is cluster-wide.
- **NetworkPolicies**: see [Network policies](#network-policies).
- Optionally an Ingress, a PodDisruptionBudget, a ServiceMonitor, a Grafana dashboard ConfigMap and a ResourceQuota for the agents namespace.
- With `agent-sandbox` and a warm pool, a SandboxTemplate and a SandboxWarmPool.

The chart does **not** install PostgreSQL, your ingress controller, TLS certificates or DNS, or Agent Sandbox's controller.

<Callout type="info" title="One replica, or two">
The chart's default is one replica. The Deployment then replaces its pod instead of rolling it, so every change has a short outage. Set `replicaCount: 2` and `podDisruptionBudget.enabled: true` to stay up through node drains and rollouts: see [Running several replicas](/docs/operate/replicas).
</Callout>

## Before you install

1. **Kubernetes 1.27 or newer, Helm 3 or 4**, and a **CNI that enforces NetworkPolicy** (Cilium, Calico, or kindnet in recent kind). A CNI that ignores NetworkPolicy, such as flannel on its own, leaves agents un-isolated and says nothing. See [Check that policies are enforced](#check-that-policies-are-enforced).
2. **PostgreSQL 17** with two databases: the platform's, and the agents' with a role that has `CREATEROLE` and `CREATE` on it. See [Databases](/docs/operate/databases). Any PostgreSQL 17 the cluster can reach works, managed services included. The repository has an example for CloudNativePG, with the NetworkPolicies its pods need.
3. **An OIDC client** at your identity provider, with the redirect URI `https://agents.example.com/auth/callback`. See [OIDC sign-in](/docs/operate/oidc).
4. **An ingress controller and TLS** for the host in `appUrl`. The platform refuses a non-loopback `http://` address.
5. For the `agent-sandbox` launcher, [Agent Sandbox](https://agent-sandbox.sigs.k8s.io) with its extensions (SandboxTemplate, SandboxWarmPool and SandboxClaim) installed first.

## 1. The namespace and the Secret

The chart creates the agents namespace, not the platform's. Create it, and the Secret the platform reads:

```sh
kubectl create namespace pi-durable-platform
kubectl label namespace pi-durable-platform pod-security.kubernetes.io/enforce=restricted
kubectl -n pi-durable-platform create secret generic pi-durable-platform \
  --from-literal=DATABASE_URL='postgres://pdp:<password>@db.example.com:5432/pdp?sslmode=require' \
  --from-literal=AGENTS_DATABASE_URL='postgres://pdp_agents_admin:<password>@db.example.com:5432/pdp_agents?sslmode=require' \
  --from-literal=ENCRYPTION_KEY="$(openssl rand -base64 32)" \
  --from-literal=API_KEY_PEPPER="$(openssl rand -base64 32)" \
  --from-literal=OIDC_CLIENT_SECRET='<from your identity provider>'
```

| Key | |
|---|---|
| `DATABASE_URL` | Required: the platform's database |
| `AGENTS_DATABASE_URL` | Required: the agents database, with the provisioning role. Its host must resolve from the agents namespace (`service.namespace.svc`), or set `agents.runtimeDatabaseHost` |
| `ENCRYPTION_KEY`, `API_KEY_PEPPER` | Required: `openssl rand -base64 32` each, with different values |
| `OIDC_CLIENT_SECRET` | With OIDC |
| `ENCRYPTION_KEY_PREVIOUS`, `API_KEY_PEPPER_PREVIOUS`, `AGENTS_MODEL_API_KEY` | Optional: during [key rotation](/docs/operate/key-rotation), and for an OpenAI-compatible default model |

Keep `ENCRYPTION_KEY` and `API_KEY_PEPPER` with your backups: a database backup is useless without them. Secrets are never rendered into a manifest, the ConfigMap or the chart's values. A setting can come from another Secret, for example `secrets.databaseUrl: {name: pdp-db-app, key: uri}`. The repository's `deploy/secrets.example.yaml` shows the same Secret with fake values.

If the Secret is missing, the pod waits in `CreateContainerConfigError` until it exists.

## 2. The values

Write a `values.yaml`:

```yaml
appUrl: https://agents.example.com
oidc:
  issuer: https://idp.example.com/application/o/pi-durable-platform/
  clientId: pi-durable-platform
  allowedGroups: [pi-durable-users]           # optional: limit sign-in to IdP groups
  bootstrapAdminSubject: "<your OIDC subject>" # becomes platform admin on first sign-in
trustedProxies: [10.244.0.0/16]               # your ingress controller's pod CIDR
ingress:
  enabled: true
  className: nginx
  tls:
    - secretName: pdp-tls
networkPolicy:
  kubeApiServer:
    cidrs: [192.0.2.10/32]                    # the API server's address, see below
  database:
    podLabels:
      cnpg.io/cluster: pdp-db                 # your PostgreSQL pods (or cidrs: [...])
  ingress:
    from:                                     # who may reach the web port
      - namespaceSelector:
          matchLabels:
            kubernetes.io/metadata.name: ingress-nginx
```

With `oidc.allowedGroups` set, the chart adds the `offline_access` scope to `OIDC_SCOPES` for you, because the platform needs each person's refresh token to [re-check their groups](/docs/operate/oidc#re-checking-groups) while they are signed in. **Your identity provider must issue refresh tokens for that scope to this client.** The chart leaves `offline_access` out only if you turn the re-check off with `oidc.groupRecheckInterval: "0"` (a string). `groupRecheckInterval` and `groupRecheckGrace` are strings such as `"30m"` and `"24h"`; left empty, the platform's defaults apply (15 minutes and 24 hours).

With the standard NetworkPolicy flavour, the platform can reach the Kubernetes API only by address, because a standard policy can't name it. Find it:

```sh
kubectl get endpointslices -l kubernetes.io/service-name=kubernetes \
  -o jsonpath='{.items[0].endpoints[*].addresses[*]}'
```

and list each address as a `/32`. The chart refuses to render without it, rather than leave the launcher unable to start agents. With Cilium, use [`flavor: cilium`](#network-policies) instead and no address.

## 3. Install

Pin both images by digest, from the [release notes](/docs/releases/v0-2-0#images-and-chart). Without a digest the default tag is `v<appVersion>`, the release the chart belongs to. For v0.2.0:

```sh
helm install pi-durable-platform oci://ghcr.io/ncecere/charts/pi-durable-platform --version 0.2.0 \
  -n pi-durable-platform -f values.yaml \
  --set images.platform.digest=sha256:3f988afa89eadec2b4f38b132cc34016300e10d11e7c08c0258a6546b195222d \
  --set images.runtime.digest=sha256:11a098887c13377c985dae169d7dbbaedc854717b1d277e3cdf5aec45602ce8e
```

The chart is published, and signed, to `oci://ghcr.io/ncecere/charts/pi-durable-platform` for each release tag; its version is the release's (v0.2.0 is chart 0.2.0). From a checkout of the repository you can install `deploy/helm/pi-durable-platform` instead: its images are the release named in its `Chart.yaml`.

### Verify the chart

Verify a published chart with [cosign](https://docs.sigstore.dev/cosign/system_config/installation/) v3.0 or newer (keyless, GitHub Actions OIDC), as you verify the images:

```sh
cosign verify ghcr.io/ncecere/charts/pi-durable-platform:0.2.0 \
  --certificate-identity https://github.com/ncecere/pi-durable-platform/.github/workflows/chart.yml@refs/tags/v0.2.0 \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

Chart 0.2.0 has the digest `sha256:328a90a22c2d2a82a1e74a7b9667f3fa4bfe5d8ddd8a950967f7596b1a106cb8`. The images are verified with the identity of the `image.yml` workflow, as the [release notes](/docs/releases/v0-2-0#verifying-the-images-and-the-chart) show.

## 4. Check it

```sh
kubectl -n pi-durable-platform rollout status deploy/pi-durable-platform
kubectl -n pi-durable-platform exec deploy/pi-durable-platform -- /pi-durable-platform doctor
```

`doctor` checks the configuration, both databases, migrations, the agents provisioning role and the keys. See [Doctor and health checks](/docs/operate/doctor-and-health). Then sign in at `appUrl`. The person whose OIDC subject is `oidc.bootstrapAdminSubject` becomes platform admin at their first sign-in, once. Teams, agents, models and MCP servers are managed in the web app, not by the deployment.

Agents use the scripted `demo` model until you add a provider in **Admin › Models**, or set `agents.model`.

## Launchers

- `agents.launcher: kubernetes` (the default): one pod per agent.
- `agents.launcher: agent-sandbox`: install Agent Sandbox first. With the warm pool (`agentSandbox.warmPool.enabled` and `size`), the chart creates the SandboxTemplate and the SandboxWarmPool, and the platform creates the pool's activation Secret (`agentSandbox.activationSecret`) itself. Without it, each agent is a Sandbox that is suspended when idle.

See [Agent Sandbox and warm pools](/docs/operate/agent-sandbox).

The Role the chart creates has the verbs of the launcher you choose:

| Launcher | Rules in the agents namespace |
|---|---|
| `kubernetes` | pods: get, list, watch, create, delete; secrets: get, create, update, delete |
| `agent-sandbox`, warm pool | sandboxclaims: get, list, watch, create, delete; secrets: get, create, delete |
| `agent-sandbox`, no warm pool | sandboxes: get, list, watch, create, patch, delete; pods: get; secrets: get, create, update, delete |

## Values

`values.yaml` in the chart documents every value, and `values.schema.json` rejects unknown keys and wrong types. The ones you will set:

| Value | |
|---|---|
| `appUrl` | Required: the public origin |
| `images.platform`, `images.runtime` (`tag`, `digest`) | The default tag is `v<appVersion>`; pin by digest |
| `secrets.name`, and a `{name, key}` for each setting | Where the database URLs, the two keys and the OIDC secret are read |
| `oidc.*` | Issuer, client ID, claims, `scopes`, `allowedGroups`, `allowedEmailDomains`, `bootstrapAdminSubject`, and `groupRecheckInterval` and `groupRecheckGrace` (strings). With `allowedGroups`, the chart adds the `offline_access` scope: see [Re-checking groups](/docs/operate/oidc#re-checking-groups) |
| `agents.*` | Namespace, launcher, idle timeout, runtime class, pull Secret, database host for runtimes, default model, apps' MCP hosts, quota |
| `agentSandbox.*` | Warm pool on or off and its size, names, runtime resources |
| `ingress.*` | Class, host (default: the host of `appUrl`), path, TLS, annotations |
| `networkPolicy.*` | See [Network policies](#network-policies) |
| `resources`, `podSecurityContext`, `securityContext` | Defaults are restricted: non-root, read-only root filesystem, no capabilities, seccomp |
| `terminationGracePeriodSeconds` | 75 by default. The platform waits `SHUTDOWN_DELAY` (5 s) and then gives requests and event streams `SHUTDOWN_TIMEOUT` (60 s) to finish, and the pod needs both. If you raise either setting, raise this too |
| `replicaCount` | 1 by default; 2 is the supported setup for staying up. See [Running several replicas](/docs/operate/replicas) |
| `podDisruptionBudget.*` | Off by default: with one replica, a budget of `minAvailable: 1` blocks node drains. Turn it on with two replicas |
| `affinity`, `topologySpreadConstraints` | When set, they replace the spreading defaults that more than one replica gets |
| `metrics.*` | `enabled` (on by default), `port` (9090), `serviceMonitor.*` (for the Prometheus Operator) and `dashboard.*` (the Grafana dashboard as a ConfigMap, off by default). See [Metrics and tracing](/docs/operate/metrics-and-tracing) |
| `tracing.*` | `otlpEndpoint` (an OTLP/HTTP collector's base URL; empty means no tracing), `serviceName`, `sampleRatio` |
| `config`, `extraEnv`, `extraEnvFrom`, `extraVolumes` | Any other [setting](/docs/operate/configuration) of the platform, for example `config: {OIDC_GROUP_RECHECK_INTERVAL: 30m}` |

The ConfigMap holds every non-secret setting. The pod restarts when it changes (`rolloutOnConfigChange`).

## Network policies

The policies are what isolates agents. They need a CNI that enforces them.

- **Agents namespace**: everything is denied. An agent pod takes traffic only from the platform (port 4100) and reaches only its PostgreSQL (5432), the platform's gateway (8099) and cluster DNS. It can't reach other agents, the platform's web port, the Kubernetes API or the internet.
- **The platform's pods**: web traffic (8098) from the peers you list in `networkPolicy.ingress.from`, and the gateway port from agent pods only. They reach DNS, PostgreSQL, agent pods (4100), the Kubernetes API, and public HTTPS (the identity provider, model providers and MCP servers by their public names; private ranges are excluded).

`networkPolicy.*` has these settings:

| Value | |
|---|---|
| `flavor` | `standard` (Kubernetes NetworkPolicy only, with `kubeApiServer.cidrs`) or `cilium` (also a `CiliumNetworkPolicy` that allows the `kube-apiserver` entity, so no address is needed) |
| `kubeApiServer.cidrs`, `ports` | The API server's addresses and ports (443 and 6443), for the standard flavour. Required there |
| `database` | Required: PostgreSQL's pods (`podLabels`, in `namespace`, by default the release's) and/or external `cidrs`, and `port`. The platform and agent pods may reach them. PostgreSQL's own pods need ingress from both: if your namespace denies by default, allow it |
| `ingress.from` | Who may reach the web port. The default is every namespace: narrow it to your ingress controller's |
| `egress.publicHttps` | Public HTTPS egress for the platform, with the private ranges excluded |
| `metrics.from` | Who may reach the metrics port (9090), written as NetworkPolicy `from` peers. The default is nobody: no rule is created, so nothing can scrape the port until you name your scraper |
| `egress.tracing` | Where the tracing collector is (`to`, and `ports`, 4318 by default), when it is in the cluster or on a private address |
| `egress.extra`, `agents.extraEgress` | More egress rules for the platform pods and for agent pods, for direct-mode providers and MCP servers on addresses agents otherwise can't reach |

`networkPolicy.enabled: false` removes every policy, and agents are then **not isolated**. Only do that where something else enforces the same rules.

See [Network isolation](/docs/operate/network-isolation) for the connections each side needs.

### Check that policies are enforced

A cluster whose CNI ignores NetworkPolicy accepts the objects and enforces nothing. Check, as the repository's smoke test does: from an agent pod, a connection that should be refused must be refused.

The smoke test (`deploy/scripts/smoke-kind.sh`) installs the chart into a kind cluster, whose default CNI, kindnet, enforces NetworkPolicy. It checks that `doctor` passes, that the launcher has the rights it needs and no more, that an agent answers a message and hibernates and wakes, and that from an agent pod only the database and the gateway are reachable (not the web port, the Kubernetes API, the internet or another agent) and that a pod outside the platform can't reach an agent. It installs **two replicas** and checks that a session, an agent and its conversation are shared between them. Continuous integration runs it for every change to `deploy/`, with the images built for that commit. Run by hand, it installs the images the chart names unless you give it others.

## Upgrading

Set the new chart version, and the new release's digests, and run `helm upgrade`. The platform applies its migrations at start (`migrateOnStart`, on by default). A single replica is replaced, not rolled, so there is a short outage. Several replicas roll one at a time with none missing, so both versions run for a while. A warm pool replaces its standby runtimes at once. Agents that are running move to the new runtime image when they next wake. See [Upgrades and migrations](/docs/operate/upgrades).

## Uninstalling

`helm uninstall` keeps the agents namespace (`agents.keepNamespace`), because deleting it deletes every agent's Secret. The databases are yours.

## What the chart doesn't include

- PostgreSQL, and its backups.
- The ingress controller, TLS certificates and DNS.
- Agent Sandbox's controller and CRDs.
- Prometheus, Grafana and a tracing backend. The chart ships what they need: see [Metrics and tracing](/docs/operate/metrics-and-tracing).
- Direct-mode providers and MCP servers on private addresses: agents reach only the database, the gateway and DNS. Give them more with `networkPolicy.agents.extraEgress`, and the platform with `networkPolicy.egress.extra`.
