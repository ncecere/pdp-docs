Pi Durable Platform uses two PostgreSQL databases. They can be on the same server, but must be separate databases.

| | Platform database | Agents database |
|---|---|---|
| Setting | `DATABASE_URL` | `AGENTS_DATABASE_URL` |
| Holds | People, teams, templates, agents' records, thread records, keys (as digests), sealed secrets, usage, the audit log, rate-limit counters, sessions | One schema per agent: its conversations, in Pi's durable storage |
| Who connects | The platform | The platform's provisioning role, and each agent's runtime with its own role |
| Schema changes | The platform's migrations | Created per agent by the platform |

Use PostgreSQL 17, the version the platform is developed and tested with. The agent provisioning relies on PostgreSQL 16 or later.

## The platform database

Create a database and a role that owns it:

```sql
CREATE ROLE pdp LOGIN PASSWORD '...';
CREATE DATABASE pdp OWNER pdp;
```

The platform's migrations create everything inside it. See [Upgrades and migrations](/docs/operate/upgrades).

Then close it to everyone else. PostgreSQL lets `PUBLIC`, so every role, connect to a database it creates, and agents' roles are roles of the same server:

```sql
REVOKE CONNECT ON DATABASE pdp FROM PUBLIC;
GRANT CONNECT ON DATABASE pdp TO pdp;
```

Grant `CONNECT` to any other role that uses the database too. See [Where agent roles can connect](#where-agent-roles-can-connect).

## The agents database

Create a second database owned by a **provisioning role** with `CREATEROLE`. It needn't be a superuser:

```sql
CREATE ROLE pdp_agents_admin LOGIN CREATEROLE PASSWORD '...';
CREATE DATABASE pdp_agents OWNER pdp_agents_admin;
```

`pi-durable-platform doctor` checks this setup: that the agents database answers, runs PostgreSQL 16 or later, and that the role in `AGENTS_DATABASE_URL` has `CREATEROLE` and `CREATE` on it. See [Doctor and health checks](/docs/operate/doctor-and-health#the-agents-database-checks).

At start-up the platform hardens this database once: `PUBLIC` loses all rights on schema `public` and the right to create temporary tables. Making the provisioning role the database's owner gives it the rights to do that.

For each agent it then creates:

- a **login role** `agent_<id>`, with a random password, `NOINHERIT NOCREATEDB NOCREATEROLE` and a connection limit of 2;
- a **schema** of the same name, owned by that role.

The agent's role owns only its schema and has no rights on any other, so one agent can't read another's conversations. The provisioning role is never given to agents.

Deleting an agent stops its role from signing in, ends its sessions, drops its schema and anything else the role created in the agents database (large objects or stray tables, for example), then drops the role. Each step can be repeated: if one fails, the agent stays, with an error, and deleting it again finishes.

`AGENTS_CREATE_DATABASE=true` makes the platform create the agents database through `DATABASE_URL` at start-up. It's for development and refused on a reachable host.

### How runtimes connect

Each runtime gets a connection URL built from `AGENTS_DATABASE_URL`: the same host, database and TLS settings (`sslmode` and so on), with the agent's own role and password. If agent pods reach PostgreSQL by another address than the platform (another DNS name, a pooler), set `AGENTS_RUNTIME_DATABASE_HOST` to that `host:port`.

A runtime holds **one** connection for its lifetime, and that connection's session is how a single runtime owns an agent: the owner is recorded in a table in the agent's own schema (see [Who owns an agent](#who-owns-an-agent)). Don't put a transaction-mode connection pooler between runtimes and PostgreSQL: ownership needs a session that lasts, and each runtime's session must be visible in `pg_stat_activity`. A runtime refuses to start when its own session isn't visible there, which is the case when the server has `track_activities` off. It's on by default.

### Who owns an agent

One runtime at a time writes for an agent, and a replacement takes over as soon as the owner is gone, whether it crashed, lost its connection or was terminated. The runtime keeps a one-row table, `pdp_ownership`, in the agent's schema. It records the owner's database session. To take ownership, a runtime locks that row, then checks whether the recorded session still exists. If it does, the runtime refuses to start and the platform tries again. If not, it records itself as the owner. A clean stop clears the record.

Because the record is in the agent's own schema, only that agent's role can write it. Another agent's role gets "permission denied" on the table and can't block, take or change the ownership of an agent that isn't its own. The agent's own role can of course change its own record and data.

The runtime creates the table itself, with the agent's own role, the first time a runtime of this version starts the agent. There is nothing to migrate: agents move as they next wake.

While runtimes of an older release may still run (an old pod during a rollout, or an agent woken with an old image), the new runtime also takes the older release's advisory lock on its connection, and refuses to start if a session of the agent's own role holds it. A holder running as any other role is ignored. The older lock stays until no older runtime is left.

### Where agent roles can connect

An agent's role is a login role of the PostgreSQL **server**, and the runtime that holds its password runs code the platform doesn't trust. Schema rights keep it inside its own schema of the agents database. But unless you revoke it, PostgreSQL lets every role connect to every database on the server, including the platform database. There, a role could take the platform's advisory locks (waking an agent, the idle reaper, migrations) and stop agents from waking or the platform from starting.

So the database server is a trust boundary you configure:

1. **Revoke `CONNECT` from `PUBLIC`** on the platform database, and grant it to the platform's role, as shown in [The platform database](#the-platform-database). Do the same for the other databases on that server that agents must not reach, including `postgres`.
2. Or, in addition, **limit agent roles to the agents database in `pg_hba.conf`**. Agent roles are named `agent_` followed by the agent's ID without dashes, and PostgreSQL 16 or later reads a name that starts with `/` as a regular expression. Put these rules before any broader ones:

   ```text
   host pdp_agents /^agent_ all scram-sha-256
   host all        /^agent_ all reject
   ```

The repository's CloudNativePG example (`deploy/examples/cloudnative-pg/`) does both. The platform doesn't revoke anything itself, because other roles may depend on connecting to those databases.

`doctor` warns while `PUBLIC` may connect to the platform database, with the statements to run. When both databases are on the same server, it also lists the other databases there that `PUBLIC` may connect to. See [Doctor and health checks](/docs/operate/doctor-and-health#the-database-access-checks).

The agents database itself can't be closed to agent roles. Nothing the platform needs there depends on a lock an agent could hold: an agent's role holding the lock that serialises replicas' start-up can't block it.

### Size

Each agent's schema holds about 25 tables and indexes. That's fine for thousands of agents. Count connections: one per running agent, plus the platform's pools. Each platform replica also holds a connection that listens for thread events and takes short-lived ones for its locks: see [Running several replicas](/docs/operate/replicas#postgresql-connections).

## Clean-up

Roles are server-wide in PostgreSQL. If an agent's deletion fails halfway, or you restore an older platform database, schemas and roles may be left that no agent owns. Remove them with:

```sh
pi-durable-platform prune-agent-storage --dry-run   # list them
pi-durable-platform prune-agent-storage             # remove them
```

Run it while no agents are being created. It only considers schemas in the agents database `AGENTS_DATABASE_URL` names.

### Roles left by a dropped agents database

A role outlives the database it was made for. If you drop or recreate the agents database, its agents' roles stay on the server. `doctor`'s `agents roles` check lists them (see [Doctor and health checks](/docs/operate/doctor-and-health#the-agent-roles-check)), and `prune-roles` drops them:

```sh
pi-durable-platform prune-roles --dry-run   # list what would be dropped, and what is kept and why
pi-durable-platform prune-roles             # drop them
```

Run it while no agents are being created, with `--dry-run` first. The platform marks each role it creates with a comment naming its agents database. `prune-roles` drops a role only when it:

- is named like an agent's (`agent_…`), belongs to no agent in the platform database, and has no schema in the agents database;
- is a role made the way the platform makes them: no privileged attributes and no memberships, managed by the provisioning role, and not marked for another agents database (it may have lost its login, which a half-finished deletion leaves);
- has no open sessions.

It drops what the role still owns in the agents database, such as a large object or a table it created. It touches nothing in any other database: if PostgreSQL finds that the role still owns objects, or has privileges, in another database, the role is kept and listed with the reason. That protects a live agent of another installation on a shared server, which owns its schema in another database. Roles made before the comment existed carry no mark, and are still considered: only those that own nothing in other databases can go.

## Known limits

- Agents' roles share the server's connection and CPU capacity: there are no per-role quotas beyond the connection limit, and any role can see that other roles' sessions exist (`pg_stat_activity` shows user names and process IDs). A hostile agent could still be a noisy neighbour. That's acceptable while agents run only reviewed templates; it is part of why agents can't run uploaded code yet.
- Every commit is a network round trip to PostgreSQL. Place runtimes and the database close together.
