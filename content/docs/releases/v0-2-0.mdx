Pi Durable Platform v0.2.0, released on 2026-10-19, is "Run it anywhere, safely", on top of [v0.1.2](/docs/releases/v0-1-2). The platform now ships deployment manifests, runs as several replicas, exports metrics and traces, and can re-encrypt its secrets. It closes the safety gaps the v0.1.0 notes listed, and fixes what an independent review of this release found.

It includes **database migration 17**. Read [Upgrading from v0.1.2](#upgrading-from-v012) first.

## What changed

### Deploying

- **A Helm chart and a Kustomize base**, with RBAC, NetworkPolicies (and a Cilium flavour), Pod Security `restricted`, the Kubernetes and Agent Sandbox launchers, an Ingress, a PodDisruptionBudget and a ResourceQuota. The chart is the source of truth: the Kustomize base is generated from it, and CI checks that both render the same objects, with Helm 3 and Helm 4. The chart is published, signed with cosign, to `oci://ghcr.io/ncecere/charts/pi-durable-platform`. CI installs it into a kind cluster with two replicas and checks the isolation: an agent reaches only its database, the gateway and DNS. See [Install on Kubernetes](/docs/operate/kubernetes) and [Kustomize](/docs/operate/kustomize).
- **Several platform replicas.** Set `replicaCount: 2` (with Kustomize, the `components/replicas` component). The chart rolls updates without leaving a replica missing, spreads the pods over nodes and zones and, if you turn it on, adds a PodDisruptionBudget. The runtime reports its open streams and its work, and the idle reaper believes that report. Only one replica reaps at a time, and starting an agent is serialised across replicas, so no replica hibernates an agent whose stream is open on another. See [Running several replicas](/docs/operate/replicas).
- **Metrics and tracing.** `GET /metrics` on its own listener (`METRICS_ADDR`). The chart turns it on, on port 9090, and lets nobody reach it until you name your scraper. It covers requests by route pattern, agent wakes, hibernations, the model and MCP proxies, OAuth, sign-ins, rate limits, background loops, group re-checks and database pools. Labels are values the platform defines: never an ID, an email, a team name or a URL. Traces are optional, over OTLP/HTTP (`OTEL_EXPORTER_OTLP_ENDPOINT`). The repository has a Grafana dashboard and example alerts, and the chart can create a ServiceMonitor, the NetworkPolicy for your scraper and the dashboard's ConfigMap. See [Metrics and tracing](/docs/operate/metrics-and-tracing).

### Operating

- **`pi-durable-platform rekey`** re-seals every stored secret under the current `ENCRYPTION_KEY`: agent credentials, model providers, MCP servers and the stored identity provider tokens. `--dry-run` shows what it would do, and `doctor` counts the values still under the previous key. Once it reports none, `ENCRYPTION_KEY_PREVIOUS` can go. See [Key rotation](/docs/operate/key-rotation).
- **A configuration reference.** The repository's `.env.example` lists every setting, and a test keeps it complete. See [Configuration](/docs/operate/configuration).
- **The agents database is harder to interfere with.** An agent's ownership is a row in its own schema, taken over only when the owning database session is gone, so another agent's role can't block it. New commands: `prune-roles` and `prune-agent-storage`. `doctor` reports agent roles that belong to no agent, and warns when PUBLIC may connect to the platform database. See [Databases and roles](/docs/operate/databases).
- **Vulnerability checks in CI**: `govulncheck` and audits of the web app's and the runtime's production dependencies, weekly and whenever a dependency file changes.

### For apps and people

- **Platform-chosen thread IDs.** `POST /v1/agents/{id}/threads` returns a new, random thread ID. MCP servers are set only on a thread that exists, or that the same `PUT` creates: the caller becomes its creator (send `visibility` on the `PUT` for a private thread). Use the `POST`, and your threads can't be pre-seeded. See [Start a thread](/docs/build/threads-and-messages#start-a-thread) and [Thread MCP servers](/docs/build/thread-mcp-servers).
- **Group re-checks.** With `OIDC_ALLOWED_GROUPS`, the platform asks the identity provider every 15 minutes (`OIDC_GROUP_RECHECK_INTERVAL`) whether each recently active person is still in an allowed group. When not, their sessions, API keys and connected apps stop working, open event streams close, and **Admin › Users** shows **Group access ended**. Signing in again restores access. If the provider can't answer, access lasts a grace period (`OIDC_GROUP_RECHECK_GRACE`, 24 hours). It needs the refresh token of the person's sign-in, so the `offline_access` scope. A person without a stored token is never re-checked: this is logged, counted and shown by `doctor`. See [Re-checking groups](/docs/operate/oidc#re-checking-groups).

### Fixed and hardened

These are the result of an independent review of this release. None was known to be exploited.

- The reaper reads a runtime's `/status` through a 64 KiB limit. An agent could otherwise send a reply large enough to exhaust the platform's memory.
- Agents whose database role created large objects or stray tables can be deleted. `prune-roles` removes such leftovers.
- An agent's role can no longer block the platform's start-up by holding the agents database's prepare lock.
- A client's `traceparent` no longer forces a request to be traced.
- Open event streams check access again every 30 seconds. A person who is suspended, denied by the group re-check or removed from a team stops receiving events.
- MCP servers set on a reserved thread ID don't reach another person's first message.
- A stored identity provider token that can't be opened ends access after the grace period, instead of exempting the person. A rotated refresh token survives a restart in the middle of a check. People in more than 200 groups are matched on the full list.
- A status report from an agent's runtime that arrived after a thread was deleted brought the thread back, as a shared record with the deleted thread's title, even for a private thread. This was in v0.1.x too. A single report now only updates a thread the platform has; the runtime's list at start-up still adopts threads the platform doesn't know.
- A reserved thread (one with no message yet) can be deleted. Before, the delete answered 404, because the runtime has no conversation for it.
- `golang.org/x/net` 0.60.0 fixes four HTTP/2 advisories (GO-2026-6603, GO-2026-6611, GO-2026-6612 and GO-2026-6617) that `govulncheck` reports as reachable. **v0.1.2 and earlier are affected.**

The full list is in the repository's [CHANGELOG.md](https://github.com/ncecere/pi-durable-platform/blob/v0.2.0/CHANGELOG.md) and its [release notes](https://github.com/ncecere/pi-durable-platform/blob/v0.2.0/docs/releases/v0.2.0.md).

## Upgrading from v0.1.2

<Steps>
<Step>

**Back up the platform database.** The migration is forward-only in practice: see [Rolling back](#rolling-back).

</Step>
<Step>

**Replace both images**, the platform and the runtime, by digest, and restart. The platform applies migration 17 when it starts.

- It deletes MCP servers that were set on a thread nobody had started. Earlier releases accepted them, and a later private thread with that ID would have inherited them. From now on a thread's servers belong to its record.
- It adds the tables for group re-checks. Nobody is re-checked until they sign in again, so the upgrade locks nobody out.
- With several replicas, a rolling upgrade runs both versions for a while. Until every replica is upgraded, a request that sets MCP servers on an unrecorded thread can fail. Apps that use `POST /v1/agents/{id}/threads` are unaffected.

</Step>
<Step>

**Agents upgrade as they wake.** An agent that was already running keeps its old runtime until it hibernates. Until then it doesn't report its open streams, so the reaper judges it by the streams of the replica it is on. An agents database from v0.1.x works with the new runtime without any step.

</Step>
<Step>

**Keep agents' roles out of the platform database.** Run `pi-durable-platform doctor`. If it warns that PUBLIC may connect, run this on the database server, as the platform database's owner:

```sql
REVOKE CONNECT ON DATABASE <platform database> FROM PUBLIC;
GRANT CONNECT ON DATABASE <platform database> TO <the platform's role>;
```

Grant `CONNECT` back to any other role that uses that database. Run the same `REVOKE` for the other databases on that server that agents must not reach, or limit agent roles to the agents database in `pg_hba.conf`. The repository's CloudNativePG example (`deploy/examples/cloudnative-pg/`) has such a rule. The platform doesn't do this itself, because other roles may connect to those databases. See [Databases and roles](/docs/operate/databases#where-agent-roles-can-connect).

</Step>
<Step>

**If you set `OIDC_ALLOWED_GROUPS`**, your identity provider must issue refresh tokens for the `offline_access` scope. The Helm chart adds the scope for you. Otherwise add it to `OIDC_SCOPES`, and allow refresh tokens for the client in the provider. People then sign in again to store a token. `doctor` says how many recently active people have none, and the `pdp_group_recheck_people{state="without_token"}` metric tracks it. Without `OIDC_ALLOWED_GROUPS`, nothing changes. See [Re-checking groups](/docs/operate/oidc#re-checking-groups).

</Step>
<Step>

**Metrics are off unless you set `METRICS_ADDR`.** The chart sets it, on port 9090, and the port is unreachable until `networkPolicy.metrics.from` names your scraper. Tracing is off unless `OTEL_EXPORTER_OTLP_ENDPOINT` is set.

</Step>
<Step>

**New settings**, all optional: `METRICS_ADDR`, `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_SERVICE_NAME`, `OTEL_TRACES_SAMPLER_ARG`, `OIDC_GROUP_RECHECK_INTERVAL` and `OIDC_GROUP_RECHECK_GRACE`. See [Configuration](/docs/operate/configuration).

</Step>
</Steps>

More detail is in [Upgrades and migrations](/docs/operate/upgrades#upgrading-to-v02).

### Rolling back

Going back to v0.1.2's images works, but the schema stays at migration 17. v0.1.2 ignores group denials, so people who lost access get their API keys back until you upgrade again. A request that sets MCP servers on an unrecorded thread fails. A down migration for 17 exists; it discards the group re-check tokens and denials.

## Known limitations

Unchanged from [v0.1.0](/docs/releases/v0-1-0#known-limitations), except these, which this release resolves: one platform replica, no re-encryption command, no deployment manifests, no metrics, tracing or dashboards, advisory locks in the agents database, and thread IDs chosen by clients. For the advisory locks, step 4 above is what remains: a database server is a trust boundary you configure. For thread IDs, use `POST /v1/agents/{id}/threads`; a client-chosen ID still works.

New or remaining:

- **Per-replica caches.** Each replica caches the identity provider's discovery document and apps' logos itself. With two replicas, a consent page can show an app's initials instead of its logo on some requests.
- **The `local` launcher is one process** and can't be shared between replicas. The chart offers only the `kubernetes` and `agent-sandbox` launchers.
- **The agent limit can be exceeded by one** under concurrent wakes (`too_many_running`).
- **Traces stop at the runtime.** The platform passes `traceparent` to the runtime, but the runtime doesn't read it, so its own model and MCP calls start new traces.
- **Open streams and keys.** A stream closes within 30 seconds when a person loses access. A revoked API key or app grant doesn't close a stream that is already open, and a service account key isn't re-checked.
- **Group re-checks are fail-open for people without a stored token**, so a provider that issues no refresh tokens can't lock everyone out. `doctor` and the metrics show it.

The project's [roadmap](https://github.com/ncecere/pi-durable-platform/blob/main/docs/roadmap.md) plans the rest, each with a GitHub issue with the [`roadmap` label](https://github.com/ncecere/pi-durable-platform/issues?q=is%3Aissue+label%3Aroadmap).

## Verifying the images and the chart

Verify the signatures with [cosign](https://docs.sigstore.dev/cosign/system_config/installation/) **v3.0 or newer** (keyless, GitHub Actions OIDC). The images are signed by the `image.yml` workflow, the chart by `chart.yml`:

```sh
cosign verify ghcr.io/ncecere/pi-durable-platform@sha256:3f988afa89eadec2b4f38b132cc34016300e10d11e7c08c0258a6546b195222d \
  --certificate-identity https://github.com/ncecere/pi-durable-platform/.github/workflows/image.yml@refs/tags/v0.2.0 \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
cosign verify ghcr.io/ncecere/pi-durable-platform-runtime@sha256:11a098887c13377c985dae169d7dbbaedc854717b1d277e3cdf5aec45602ce8e \
  --certificate-identity https://github.com/ncecere/pi-durable-platform/.github/workflows/image.yml@refs/tags/v0.2.0 \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
cosign verify ghcr.io/ncecere/charts/pi-durable-platform:0.2.0 \
  --certificate-identity https://github.com/ncecere/pi-durable-platform/.github/workflows/chart.yml@refs/tags/v0.2.0 \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

Each image carries its SBOM (SPDX) and build provenance as attestations, and the release has each image's SBOM per platform with `checksums.txt`. `pi-durable-platform version` prints `pi-durable-platform 0.2.0 (<commit>)`; the runtime image is labelled `org.opencontainers.image.version=0.2.0`.
